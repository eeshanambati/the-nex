# The Nex

Local endpoint protection for Windows and macOS, written in Rust: a known-malware hash list,
zip-bomb inspection before extraction, an on-device ONNX model for new executables,
living-off-the-land process guard, and ransomware canary files, with a Tauri desktop dashboard.

**To install it, see [INSTALL.md](INSTALL.md)**: one-click `TheNexSetup.exe` on Windows and
`TheNex.pkg` on macOS, attached to each [release](../../releases).

## Repository layout

- `crates/the-nex-core`: detection engines, quarantine, platform layer
- `crates/the-nex-daemon`: the `the-nex` service / CLI (`--help` lists every mode)
- `crates/the-nex-gui`: Tauri v2 desktop app; its frontend is the plain HTML/CSS/JS in `ui/`
- `crates/aegismesh-*`: AegisMesh silent-SOS wearable simulation (core library, `aegismesh-sim`
  CLI, `aegismesh-gui` console; the console is also the AegisMesh page of The Nex app).
  Simulation only: no radio, network or emergency service is ever used. Its camera watch
  recognises emergency hand signs (the Signal for Help) and facial expressions, plus hand signs,
  expressions and movements (a wave, a circle, a swipe) you teach it; "My SOS triggers" keeps
  those and your own tap rhythms, saved on the device, with Google MediaPipe models run on-device (`scripts/fetch_vision_models.py` pins and
  verifies them, and three.js for the 3D wearable viewer; the page blocks every off-device
  connection). Recogniser tests: `node scripts/test_signs.js`. The ring, bracelet and clothing-tag
  models (`ui/aegismesh/models/`, GLB plus a still render each) are built in Blender by
  `scripts/models/build_wearables.py`; run it again after changing a model.
- `packaging/windows/installer.nsi`: Windows installer; `packaging/macos/`: app bundle, DMG and pkg
- `scripts/`: icon and model generation, live verifier, developer install scripts

CI (`.github/workflows/ci.yml`) builds, tests and live-verifies both platforms, builds both
installers, and installs and uninstalls each one on the runner. Pushing a `v*` tag publishes a
release with the installers attached.

## Desktop app

The dashboard opens on a sign-in screen (email and password, or **Create account**). Signing in
talks to Supabase Auth over HTTPS (supabase.co). While signed in the app also syncs a small device
summary (device id and name, platform, version, counts and on/off flags, no file paths) and remote
quick-scan / canary-check commands through Supabase, polling every 15 s and updating every 60 s, which
reveals your IP address and activity times to Supabase. Pasting a wallpaper URL contacts that page's host and then the image host it points to (which may differ), following redirects. The account chip asks Gravatar for a profile photo using a SHA-256 hash of your email.
Device rows and command history stay on Supabase after sign-out or uninstall until removed from the Devices page (or the account is deleted by the project owner); in-app account deletion isn't available yet. Detection itself stays on-device, and protection keeps running whether or not
anyone is signed in. On the device the session (access and refresh token, expiry, user id and email,
never the password) is kept under `thenex.session` in local storage and removed on sign-out; the
device id, theme and appearance settings are kept there too. No cookies, analytics or ads. The full
inventory is in `ui/privacy.html` (Settings → Privacy). Tests: `node scripts/test_auth.js`,
`node scripts/test_sync.js`.

On macOS a menu-bar item (gyroscope icon) offers **Open The Nex**, **Quick Scan**, **Full Scan**,
shortcuts to Activity, Quarantine and Settings, and **Quit The Nex**; closing the window keeps The
Nex running in the menu bar. On Windows the notification-area icon comes from the background
service's `--tray` mode (installed by `--install`).

**Scans.** *Quick Scan* checks Downloads and Desktop. *Full Scan* walks everywhere software can be
installed or dropped (on macOS: /Applications, /Users, /Library, /opt, /usr/local and the temp
folders; Apple's sealed system volume and external drives are left out). A full scan only reports:
it never moves, deletes or stops anything, because the model wrongly flags about 1 clean program in
200 and acting on that across a whole disk would break installed software. iCloud / File Provider
placeholders are skipped so nothing is downloaded, and any folder macOS refuses to open is named
in the result instead of being counted as clean. Both scans are run by the background service
(`the-nex --quick-scan` / `--full-scan` do the same from a terminal): the app drops an empty
request file in `<data folder>/requests`, which any local user may do, and follows
`logs/scan_progress.json`. On macOS the service needs Full Disk Access to read Desktop, Documents
and Downloads.

The icon is generated by `python3 scripts/gen_icons.py`, which also writes
`crates/the-nex-gui/icons/tray-template.png` (the macOS menu-bar template image) and `icon.ico`.

**Problem reports.** The app never sends a report itself. "Report a problem" (Settings) opens
<https://the-nex.vercel.app/report> in the browser; "Report as safe" on an Activity or
Quarantine item also copies that item's details for pasting into the form: type, score and
reasons, the file's name and hash, never the folder it was in, with the account name removed
from any other path (`ui/report.js`, tested by `node scripts/test_report.js`). The form
(`web/report.html`) stores what is typed in a Supabase table that anyone can add to and only
the project owner can read (`scripts/supabase_reports.sql`), capped at 10 reports in 24 hours per
address and 500 in total. The cap keeps a keyed code of the sender's address, apart from the
reports, and an hourly job deletes codes older than 24 hours. Not included yet: the 14 feature numbers behind an AI verdict,
which events do not record.

## Everyday features (not released yet)

- **Always allow** (Activity, Quarantine): never flags one exact file again, matched by SHA-256,
  never by name or folder; one changed byte flags it again. Needs an administrator, because
  malware must not be able to allow itself: the list lives in the service's protected folder, the
  elevated engine looks the detection up in its own log, and the prompt names the file and the
  start of its hash. Files on the known-malware list, scripts and decoy alerts can never be
  allowed. Settings lists what is allowed, with Remove. Limits: an updated program has to be
  allowed again; files over 256 MB cannot be; an archive's hash is taken by reading it again, and on Windows only
  its size and time tell whether it was swapped in between.
- **Never scan** (Settings, Exceptions; `--never-scan`, `--never-scan-file`, `--scan-again`,
  `--list-never-scan`): folders and
  files whose contents are not opened, moved or deleted by the live watch, any scan, the startup
  list or the check of running programs, and where no decoys are put. A folder covers what is put
  in it later. Every change needs an administrator, because malware must not be able to list
  itself, and is logged; scans say how many listed places they left out. Refused: whole disks,
  whole user folders, the system, the standard temporary folders, LaunchAgents and LaunchDaemons,
  and the Windows Start Menu. Not refused: less usual places that start things (Office start-up
  folders, shell profiles) and user or temporary folders moved to another drive.
  Limits: malware in a listed place is not noticed. A moved or renamed folder is scanned again,
  and so is another hard link to a listed file. Command lines are still judged, and when a decoy
  is changed, a program from a listed place can still be picked as the writer: its signature is
  read and it can be stopped. Events from before a place was listed stay in the log, and a file
  already in quarantine stays there. Dropping a file on the window, or `--scan-file` and
  `--check-file`, still checks it: that is a person asking. A damaged or tampered list is not used
  and raises an event. The path is on the elevated engine's command line, so a folder named like a
  dangerous command could get that prompt stopped.
- **Check a file** by dropping it on the window (`the-nex --check-file`): AI score, archive check
  and known-malware list, read-only, in a separate process with limits. Nothing is moved, logged
  or sent. It says what it could not check (files inside archives, signed programs are trusted
  and not scored) and never calls a file safe. Mouse only for now.
- **Startup programs** (`the-nex --list-startup`): what starts with the computer and what The Nex
  makes of each program, without changing anything. It checks the program file, not what that
  program loads or is told to do, so the best result is "No warning signs", and anything with
  instructions, unusual settings or a binary definition is "Not checked" (on the developer's Mac
  5 of 13 items). It cannot read macOS's newer Login Items list, other users' items, Windows
  services or scheduled tasks, and says so.
- **Scheduled scan** (off by default; daily or weekly): the quick-scan folders, at low priority,
  report only: it never moves anything even when Dry Run is off. It waits ten minutes after start
  or wake. It does not look at the battery. Findings already reported and unchanged are not
  reported again.
- **Summary report**: one readable HTML page in Downloads for 7 or 30 days. Folder names are left
  out unless ticked, and the account name is removed.
- **Setup checklist** (Settings): service, Full Disk Access (reported by the service itself), Dry
  Run, decoys. It does not say "All set" while an engine is off or the service is silent.

**Scripts and AppleScript.** The osascript rules stop the osascript process itself, as before. A
shell or Python command line that only mentions such a call is now reported instead of stopped,
unless it feeds text into osascript; the osascript it starts is still judged on its own. This
came from a false alarm on an installer command.

**Ransomware response.** When a decoy file changes, the busiest writer is stopped. That is weak
evidence: the live check once stopped the desktop app it was run from. A validly signed app is
now only reported; unsigned programs and signed interpreters are still stopped, so an innocent
unsigned program that is busy saving can still be picked.

**Security fixes over 0.4.1.** In 0.4.1 a program running as the user could set THENEX_DATA_DIR so
that the app's next administrator prompt ran a file of its choosing; the app now always uses the
installed engine and passes a clean environment. A program started through a link was inspected
under the link's name and skipped.

On macOS a running program was looked up by the path in its own memory: one started by a relative
path (`./x`) was not found and so not checked, one that became another program (`exec`) kept its
first verdict, and a program could rewrite that path. The process guard and the ransomware
response now ask the kernel, look again when a process becomes another program (judging it by its
own name, not by what it was), treat another name for the same file as the same program, and
check that a process is still the one they judged before ending it. No program running on the
developer's Mac lost protection at the moments this was tried (as a normal user, 18 of 425 paths
differed; `no_running_program_loses_its_protection`, run by hand).

What an ordinary user's malware can still do: end within 0.4 s; replace or delete its own file
that fast; run as a script, a library or inside a signed app or interpreter, which the AI does not
score (perl, ruby, node and others have no command-line rules either); or flood the
queue of programs to check. For programs already running when protection starts the AI and the
malware list only report, but the command-line rules still stop them.

**From a review of the whole app.** A small zip file of repeated end records kept the zip library
busy for minutes and so stopped live scanning: looking for a directory now has a time limit, and
running out is "not fully checked", not malware. A folder moved into a watched folder was not
scanned, because the system reports only the folder. The Windows installer took ownership of a
data folder someone had made beforehand and then trusted the settings in it; it now asks whose it
was first (never run on Windows). Programs and archives nobody has touched for 0.3 s no longer wait their turn
for another 0.3 s. A quarantined file gets its record before it is read again, so a crash cannot
lose it. The ransomware response checks that a process is still the one it judged. The window
does not freeze when decoys cannot be read, the decoy check respects its switch, and a sign-out is
not undone by a reply that comes late. A hard link made beforehand still defeats quarantine: the
file is reported as QUARANTINE_FAILED and stays.

**Idle cost.** On macOS the process guard read everything about every process 2.5 times a second
(17 ms of CPU each time on the developer's Mac, measured as a normal user). It now asks the kernel
which processes changed and reads only those (1.1 ms), everything once a minute, and so also sees
a process that starts the same program again with other instructions.

Checked on macOS only: 366 Rust tests, the Node tests and 16 live checks. On
Windows, GitHub's machines ran the state before never-scan: the live, installer and AI checks
passed and two unit tests failed on assumptions of their own (corrected since, not rerun);
never-scan is only type-checked there. Since then the engine, the command line, the live checks and
the app window have been run on a real Windows 11 PC; what was found and fixed there is in
[UPGRADE_LOG.md](UPGRADE_LOG.md). The administrator prompts and the installed service were not
exercised on that PC.

## Known-malware list

The first check on any file: is it, byte for byte, a file already identified as malware? The
Nex hashes the file (SHA-256) and looks the hash up in a list shipped with the app. Unlike the
AI this is not an estimate, so a match is acted on at once and logged as `KNOWN_MALWARE`,
severity critical, with the reason in plain words:

```
matched known-malware list (list of 2026-11-18, 1000000 entries) sha256=5069b8...
```

**No list ships yet.** The intended source, abuse.ch MalwareBazaar, needs a personal Auth-Key
and its data is not public domain, so nothing derived from it is in this repository and the
download is not wired in (`scripts/fetch_hash_list.py --download` explains and exits). Until a
list is licensed the engine is idle and the dashboard says "no list installed". Everything
below was built and measured with test lists: **how much real malware it catches is not
measured.**

**When it checks**

| Where | What is hashed |
|---|---|
| Watched folders (Downloads, Desktop, ...) | every new or changed file |
| Quick Scan | every file |
| Full Scan | programs, archives, scripts and documents (by type; hashing a whole disk would take hours) |
| A program starting | its program file, once per version of the file (needs the Process Guard switch on) |

**What a match does**

| Situation | Result |
|---|---|
| A file | moved to quarantine (restorable) |
| A program that just started | stopped, and its file quarantined |
| A program already running when protection started, or The Nex's own launch chain | alert only, never stopped |
| OS folders, The Nex's own files, or (macOS) a file signed by Apple | alert only: a wrong list entry must not break the computer |
| Dry run, or any Full Scan | logged as "would quarantine"; nothing is touched |
| Switch off (`the-nex --set known_bad=off`, or the Engines page) | not checked at all |

**The list file** (`known_bad.bin`, built by `scripts/fetch_hash_list.py`): a 56-byte header
(magic, entry count, date, SHA-256 of the body) and then the first 16 bytes of each file's
SHA-256, sorted. The service memory-maps it and binary-searches it. It checks the header,
length, checksum and sort order at start-up and refuses the whole file if anything is off (an
`INTEGRITY` event is logged and the other engines carry on). The installed service also
accepts only the exact list its build was made with: `--pin` writes the list's checksum into
`crates/the-nex-core/known_bad.sha256`, which is compiled in (committed as `none`). So a list
dropped next to the service later cannot decide what gets quarantined. `--hash-list <file>`
(console and one-shot scans only, never the installed service) is for testing.

**Measured** on an Apple M2, macOS 27.2, release build, with a synthetic list of 1,000,000
random entries (they match no real file):

| | Without a list | With the 1,000,000-entry list |
|---|---|---|
| List file | none | 16,000,056 bytes (16 per entry) |
| Start-up: load and verify the list | none | about 40 ms |
| One lookup | none | about 0.1 microseconds |
| Hashing a 100 MB file | none | 54 ms (about 1.9 GB/s) |
| Quick Scan of the same Downloads + Desktop (2,966 files, 9.1 GB), nothing moved | 15.6 s, 707 files read | 16.4 s, all 2,966 files read |
| Engine memory once settled | 7 MB (9 MB resident) | 8 MB (13 to 16 MB resident; under 2 MB of the mapped list stays in memory) |
| Engine CPU in its first two minutes (hashes every running program once) | 6.1 s | 8.6 s (2.5 s more, once; the same afterwards) |

Hashing uses the CPU's SHA-256 instructions. On Apple Silicon that needed the `asm` feature of
the `sha2` crate (one new build dependency, `sha2-asm`, Apple Silicon only); without it the
same Quick Scan took 28.4 s and a 100 MB file 290 ms.

**Limits**
- Exact matches only. Change one byte of a file and it no longer matches; that is what the
  other engines are for.
- The list is as old as the app. The service has no internet access, so new entries arrive
  only with a new release.
- Files over 256 MB are not hashed (7 of the 2,966 above). A Full Scan hashes only the types
  listed in `known_bad::is_listed_type`.
- New programs are noticed by polling every 0.4 s, so a listed program runs for a moment
  before it is stopped.
- Only 16 of the hash's 32 bytes are stored. The chance that a clean file matches one of a
  million entries by accident is about 1 in 10^32.
- A file in a watched folder that keeps changing is hashed again each time it settles (0.3 s
  without a write), so someone who keeps rewriting a large file there keeps the scanner busy
  and delays other checks by the time one hash takes (0.14 s for 256 MB).
- Windows: "not on the list" is remembered per program by path, size and modified time. A
  listed file swapped in with the same size and time is not noticed until the service
  restarts. Files signed by Microsoft outside the Windows folders are not recognised as OS
  files.
- The dashboard and menu bar report the engine as degraded ("no list installed") for as long as
  no list ships.
- The numbers above are macOS only.

**Try it** (harmless: the list holds only the hash of a file you choose):

```
shasum -a 256 some_file > hashes.txt
python3 scripts/fetch_hash_list.py --from-file hashes.txt --out test.bin
the-nex --quick-scan --dry-run --watch-dir <folder with some_file> --hash-list test.bin
```

Tests: `cargo test -p the-nex-core --lib` (lookups, empty, damaged, truncated and unsorted
lists, the switch, dry run, scans, a listed program being stopped), check 6 of
`scripts/verify_thenex.py` (a decoy document is quarantined, a second one is left alone, and
dry run only logs), and `python3 scripts/fetch_hash_list.py --self-test`. The measurements
come from `bench_known_bad` in `crates/the-nex-core/tests/edr_suite.rs`.

## Binary AI

New executables in watched folders (and the images of new processes) that are not validly
signed get a malware score from a small neural network running on the device (ONNX via tract;
no cloud). Every detection says why, for example:

```
score=0.972 threshold=0.65 engine=onnx; packed or encrypted code (entropy 7.95/8);
packer section names: upx0, upx1; 2 writable+executable sections; very few imports (6);
risky APIs: VirtualAllocEx, WriteProcessMemory, CreateRemoteThread; not digitally signed
```

**What it looks at** (14 features, `crates/the-nex-core/src/bin_ai.rs`): size, section
entropy (overall and at the entry point), writable+executable sections, entry-point
anomalies, import count, risky APIs (injection, keylogging, downloading, credential dumping),
signature presence, appended data, packer section names, resources, .NET and Mach-O.

**How it is trained** (`scripts/train_onnx.py`, runs in CI):
- benign: `data/benign_pe_features.csv`, features of 20,872 real Windows programs (system
  files, .NET assemblies, machine-wide and per-user apps, unsigned developer tools) from
  `scripts/build_dataset.py`, each with an anonymous number for its application, plus
  synthetic installers and macOS programs;
- malicious: synthetic profiles of documented malware traits (packed, crypted, injectors and
  stealers, droppers, obfuscated .NET, Mac stealers). No malware is downloaded or stored;
- real malware and more real clean programs: `data/ember2024_train.csv`, the measurements of
  20,000 malware and 20,000 uncertified clean Windows programs from EMBER2024 (Apache-2.0), at
  most 300 malware rows of any one family per file type. Measurements only, no program files;
- signature-blind: validly signed files are trusted and never reach the model, so a signature
  block it does see has failed verification, and anyone can staple one on. The network has no
  connection to that input at all;
- trained against free disguises: junk appended to the file and extra harmless imports;
- an ensemble of five small networks (64 and 32 units), exported as one graph;
- tested on whole applications it never saw, and calibrated so that about 0.5% of unseen real
  programs reach the quarantine threshold.

**Measured for 0.4** (the 0.3.0 model → the 0.4.1 model, on the same held-out data: five different sets of
applications this model never trained on, 20,870 program scores; the 0.3.0 model had seen
most of them):
- clean programs flagged: 0.82% → 0.46% (at the process-kill level: 0.23% → 0.13%). The 0.3.0
  model was calibrated for 0.5% with signatures counted in its favour, which production
  never does;
- malware disguised with a fake signature block, appended junk and extra imports together:
  54% → 89% detected (fake signature alone 90% → 94%);
- plain malware: unchanged for packed, crypted, injector and packed-Mac profiles (within 0.4
  points), droppers 92.7% → 90.8%, and .NET 89% → 73%. That last drop is deliberate: a quarter
  of the synthetic .NET malware is unobfuscated and has exactly the shape of an ordinary .NET
  program, and the 0.3.0 model "caught" part of it by flagging clean .NET applications (and
  lost all but 6% of its .NET detections to a few extra imports; this model keeps 76%).

The malware figures above come from synthetic profiles, so treat them as a regression benchmark,
not a real-world detection rate; the real-data numbers are in the next section. What still slips
through: droppers that pad themselves to look
like installers (62% caught with all three disguises), unobfuscated .NET malware, and anything
over 100 MB, which is not scored at all. Mac programs are the weakest spot (no real Mac
training data yet): interpreters, VMs and browsers import the same "risky" functions as
stealers, so on macOS the model leans on packing and code structure, and CI checks it against
the runner's own OS and third-party programs on every push. The fallback used when the model
file is missing is a fixed formula that still trusts signature blocks.

**Measured on real malware data (EMBER2024).** EMBER2024 (Joyce et al., 2025, Apache-2.0,
<https://huggingface.co/datasets/joyce8/EMBER2024>) is a research dataset of measurements of
real Windows programs, malware included; it contains no program files. `scripts/ember_eval.py`
turns each row into our 14 features and scores it with the shipped model through the engine's
own code. Results on the whole test split, the 0.4.1 model → the model
trained with EMBER rows (not released yet): 538,877 programs from the last 12 weeks of the data
(weekly files dated 22 September to 14 December 2024), 269,072 of them malware. The 0.4.1 model
never trained on real malware. The new one trained on the 52 weeks before these, and its settings
were chosen on the last 8 of those weeks. The split was not untouched before that: a feasibility
estimate (train on its first six weeks, judge on its last six) used it to decide whether to
retrain at all, and compared a few model sizes. No row of it is in the training sample.

| Programs | Malware caught, alert (0.65) | Malware caught, kill (0.9) | Clean, no certificate, flagged (0.65) | same (0.9) |
|---|---|---|---|---|
| All (538,877) | 37.5% → 65.8% | 24.3% → 49.1% | 3.1% → 2.2% | 1.2% → 0.2% |
| 32-bit (359,034) | 45.2% → 69.4% | 29.3% → 53.4% | 3.4% → 2.3% | 1.1% → 0.2% |
| 64-bit (119,890) | 16.9% → 62.6% | 9.4% → 46.5% | 2.7% → 1.3% | 1.4% → 0.1% |
| .NET (59,953) | 32.3% → 50.4% | 24.4% → 28.8% | 2.3% → 2.9% | 1.3% → 0.6% |

- **Clean programs.** On Windows, validly signed files never reach the model, and EMBER only
  says whether a file carries a certificate, not whether it is valid. The table counts the
  115,552 clean programs with no certificate, which the model would certainly see. On a Mac,
  Windows signatures are not checked, so every Windows program found there is scored. Over all
  269,805 clean programs: 5.3% → 3.8% at 0.65, 1.6% → 0.5% at 0.9.
- **Is it one big family?** Partly. berbew is 46,040 of the malware rows by label (any
  confidence) and went from poorly to almost fully caught. Without it: 34.7% → 58.8%. Counting
  every family with 20 or more samples equally (699 families): 36.9% → 49.9%, and 25.3% → 31.0%
  at 0.9. Families absent from the training weeks (1,066 programs): 24.5% → 38.9%.
- **At the same false-alarm rate** (thresholds set so that 0.5% of uncertified clean programs
  are flagged): 14.1% → 53.0% of malware caught.
- **Seeds:** five trainings on different splits caught 64.9% to 67.5% (mean 66.3%) and flagged
  2.0% to 2.5% of uncertified clean programs; the 0.4.1 recipe, 35.5% to 37.9% and 2.8% to 3.3%.
- **By week:** 63% to 68%, no week below the 0.4.1 model's best.
- **By malware family** (label confidence 0.7 or more, 500 or more programs; caught at 0.65):
  berbew 42.7% → 99.7%, expiro 51.7% → 91.8%, cosmu 71.6% → 99.1%, upatre 33.7% → 75.7%, neshta
  59.9% → 85.6%, njrat 13.5% → 33.5%, lummastealer 38.0% → 45.7%, triusor 6.7% → 21.0%.
- **What got worse.** Of the 699 families, 103 are caught less often at 0.65 (38 by more than 10
  points) and 237 at 0.9 (104 by more than 10 points): emotet 34.3% → 24.4% at 0.65, and among
  smaller ones pacex 97.1% → 22.3% and hckpk 85.2% → 47.1% (any label confidence); at 0.9 floxif
  21.4% → 10.1%, sality 92.6% → 69.2%, formbook 65.2% → 45.9%, remcos 60.1% → 41.1%. In all 6,098
  malware programs caught before are now missed at 0.65, against 82,244 newly caught. EMBER's
  challenge set (4,868 programs no antivirus detected when first seen) is as bad as before at
  0.65 (3.6% → 3.5%) and worse at 0.9 (2.1% → 0.7%). Clean .NET programs are flagged more at
  0.65: 2.3% → 2.9% without a certificate, 2.7% → 4.5% with one.
- **CI ships a slightly different model.** It trains on its own machines, whose arithmetic differs
  in the last digits. Simulated by nudging the starting weights, that moved the result to 66% to
  68% caught and 2.3% to 2.4% flagged, with about 1% of verdicts changed: read every figure here
  as plus or minus two points.

On our own data, mean of five splits by application (both recipes trained on each):
- real programs of unseen applications flagged: 0.73% → 0.57% (at 0.9: 0.22% → 0.06%). These
  five splits are not the ones behind the 0.46% quoted above for 0.4; on them the same recipe
  gives 0.73%, so take 0.46% as the favourable end of its range;
- synthetic malware caught: 94.4% → 92.6%, with all three disguises 89.1% → 89.7%. Every gate in
  `scripts/train_onnx.py` passes unchanged on all five splits;
- synthetic Mac stealers (reported, never gated): 51.5% → 45.3%. EMBER has no Mac programs;
- no gate covers the 0.9 level, and there synthetic detection fell (one split): packed 98.8% →
  85.2%, injectors 79.1% → 64.3%, droppers 80.2% → 70.7%, .NET 63.8% → 49.7%. Real malware at
  0.9 doubled, so the synthetic profiles and real malware disagree here.

On one developer's Mac, engine and model as shipped: 0 of 400 macOS programs flagged before and
after; third-party programs not trusted by signature 2 → 0 of 137; our own binaries and the 0.4.1
Windows installer clean. Of 21,052 scored files in the Unity editors, 28 → 25 are flagged (2 → 0
at 0.9); 14 were fixed and 11 ordinary .NET libraries are newly flagged. Not checked on Windows:
the System32 false-alarm and parity gates only run in CI.

Limits of this measurement:
- Windows only. EMBER has no Mac programs, and its non-Windows rows (PDF, APK, ELF) are left
  out, as are 1,063 programs the dataset's parser could not read. The test files list every
  program twice; each is counted once.
- Seven features are computed exactly as the engine does. Section entropies, import count,
  the entry-point checks and appended data are rebuilt from what EMBER recorded (it does not
  store section addresses, and counts a certificate as appended data; both are corrected for).
  Checked against the engine on 1,050 real clean files: all 13 comparable features agreed on
  every file. That set is almost all .NET (seven native programs, nothing packed, no
  writable+executable sections, hardly any imports), so the import, packer, W+X and
  entry-point features are unverified on the kinds of files that matter most. For 16.8% of
  rows the entry-point section could only be found from the rebuilt layout.
- The signature input is 0 for every row, as in training. In the app a file whose certificate
  fails verification reaches the model with that input set, but the model has no connection
  to it, so the score is the same.
- 0.6% of the test malware has exactly the measurements (to 4 decimals) of a training row; without
  those rows the result is the same (65.8%).

Reproduce (about 4 GB of downloads, checksummed and deleted after conversion; never in CI):
`python scripts/ember_eval.py fetch`, `score`, `report`. The training sample needs the training
files too (19 GB): `fetch --only Win32_train Win64_train Dot_Net_train`, then `train-sample`. `data/ember2024_sample.csv` is a fixed
sample of 2,040 rows of derived features (170 per file type, label and odd or even week,
with the first 16 characters of each file's SHA-256), redistributed under EMBER2024's
Apache-2.0 licence. `python scripts/ember_eval.py check` scores it with the current model
(59.2% of malware caught and 3.0% of clean flagged at 0.65, 0.4.1: 29.4% and 3.7%; the sample
has equal numbers of each file type, so it differs from the table) and fails if a retrained
model drops below 50% or flags more than 6%.

**Not scored: compiler object files.** On macOS a `.o` file (Mach-O type "object") is build
output waiting to be linked. It cannot run, is never signed, and its one segment is always
marked readable, writable and executable, which the model reads as an injector. A Full Scan of
a developer's Mac reported 12,451 findings, 12,408 of them object files; in a watched folder
they would have been quarantined mid-build. They are now left out by file type (read from the
header, not the name). Measured on the same Unity editor folder (197,031 files, 29 GB): 1,254
findings before, 28 after, and the scan took 290 s instead of 339 s. The 28 that remain are
vendor libraries (Microsoft .NET and DirectML DLLs, Unity's own runtime libraries): real false
positives of the model, listed by a Full Scan but never moved by one.

**Running programs:** stopping a process cannot be undone, so the AI only terminates (and
quarantines) a newly started program at a score of 0.90 or more; between 0.65 and 0.90, and for
anything already running when protection starts, it raises an alert instead. The Nex never acts
on its own process or the chain that launched it. Script-host (LotL) checks run before any
binary scan, so they stay fast.

**See a verdict yourself** (read-only, changes nothing):

```
the-nex --scan-file C:\path\to\program.exe     # or a folder, or @list.txt
```

**Train/serve parity:** `scripts/thenex_features.py` computes the training features in Python;
CI runs `scripts/check_feature_parity.py`, which fails if the Rust engine computes anything
different on real System32 files, if the model flags more than 2% (Windows) or 5% (macOS) of
the runner's own programs, or if our own binaries and installer are not scored clean.
